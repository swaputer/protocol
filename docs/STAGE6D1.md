# Stage 6D1: ISA toolchain foundation

Stage 6D is split into three independently testable releases: 6D1 establishes byte-level ISA/package tooling, 6D2 adds the TinySol language and compiler, and 6D3 adds full local execution plus concrete byte-fee estimation. This prevents higher-level compiler or simulation behavior from obscuring disagreements at the frozen bytecode boundary.

## ISA source binding

`docs/spec/SwapVM-ISA-v1.json` remains the only ISA source. `tooling/tinysol/scripts/generate-isa.mjs` verifies its exact v1.1 manifest Keccak-256 and SHA-256, expands `PUSH1..PUSH32`, `DUP1..DUP16`, `SWAP1..SWAP16` and `LOG0..LOG4`, rejects duplicate/range/mnemonic conflicts and generates the typed table in `src/generated-isa.ts`.

The generator independently extracts the accepted opcode ranges from production `SwapVMMiniVM._opcodeInfo` and the static-mode rejection branches from `_runCode`. Build, typecheck and CI fail if the 132-opcode accepted set, immediate widths or seven statically forbidden opcodes drift. No field was added to the frozen ISA JSON.

## Public API

The package exports:

- ISA: `INSTRUCTIONS`, lookup maps/functions, version, exact hashes and expanded metadata;
- assembly: `assemble` and readonly source-map/diagnostic/result types;
- disassembly: `disassemble`, `disassembleCode` and lossless instruction types;
- validation: `validateCode`, `instructionBoundaries`, `jumpdestBitmap`, `analyzeCode` and `assertEntrypoint`;
- packages: `encodeProgramPackage`, `decodeProgramPackage`, `validateProgramPackage`, `validatePackage`, `programPackageCodeHash`, `buildProgramPackage` and `inspectProgramPackage`;
- ABI: canonical signature validation, `functionSelector`, `eventTopic`, `interfaceId`, `exactUtf8AbiHash` and deterministic canonical JSON;
- manifests: `buildManifest` and `encodeBuildManifest`;
- binary/error helpers and stable `ToolchainErrorCode`/`ToolchainError`.

Binary entrypoints accept `Uint8Array` or even-length `0x` hex. Instruction literals are `bigint`; all externally visible objects are readonly. Errors carry stable codes plus optional byte offset, line, column and structured details, so tests never compare prose.

## Assembly and lossless disassembly

The `.svasm` grammar supports comments, labels, every frozen mnemonic, `PUSH0`, explicit `PUSH1..PUSH32`, decimal/hex literals, fixed-width bytes32 literals, `.constructor`, `.runtime`, `.abi-hash`, exact quoted `.abi-canonical`, `.code` and `.pushlabel`. Labels insert no byte. `.pushlabel` is always `PUSH2`, so relocation cannot change instruction width between passes.

Duplicate/undefined/end-of-code labels, non-boundary entries, literal overflow and code above 16,384 bytes are rejected. Explicit PUSH widths and leading zeros are retained. Canonical disassembly uses stable LF output and can be reassembled byte-identically without guessing labels or narrowing PUSH instructions.

## Consensus validator boundary

The consensus-equivalent validator rejects only the conditions rejected by Solidity `_validateCode` and `_decodePackage`: empty/oversize code, unknown opcode, truncated immediate, malformed package header/length, and entries outside opcode boundaries. It does not require `STOP`, perform stack reachability, interpret pushed values as jump targets or validate runtime dynamic jumps. `analyzeCode` reports optional warnings in a separately typed advisory channel.

## ProgramPackageV1 and sidecar

The codec implements the exact 44-byte `SVM1` header with network-byte-order `uint16` fields and the frozen trailing code. It rejects bad magic/version, short or trailing data, declared-length mismatches, empty/oversize code, bad entries, unknown opcodes and truncated immediates. `codeHash` is Keccak-256 of the complete canonical package.

The deterministic sidecar records tool name/version, ISA version and exact hashes, package/code hash, ABI/optional descriptor hash, entries, code length and SHA-256/Keccak source content hashes. It has no timestamp, absolute path, machine name or random ID and is explicitly marked `consensusEncoding: false`.

## Reference and Solidity differential method

The SRC-20, SRC-721, SRC-1155 and CPAMM fixtures are generated by losslessly disassembling the unchanged reference artifacts. Tests prove package decode → code disassembly → assembly → package encode is byte-identical, and independently verify entries, code length, ABI UTF-8 hash, full package hash, selectors, event topics and interface IDs.

The committed differential corpus contains 292 code cases and 12 package cases. It covers every possible single-byte opcode, every complete PUSH width, every truncated PUSH width, 0/1/16,384/16,385-byte code, JUMPDEST boundaries, malformed headers/entries and all reference packages. `SwapVMStage6D1.t.sol` executes that corpus through an unmodified `SwapVMMiniVM` harness and compares actual Solidity acceptance, revert selectors, offsets, bitmap, decoded fields and hashes. Regeneration is explicit; normal CI only checks committed bytes for drift.

## Scope and next stage

Stage 6D1 does not parse or type-check TinySol, compile high-level source, simulate VM state/CALL/CREATE, execute programs locally or estimate dynamic-path byte fees. Those belong to 6D2 and 6D3. No production Solidity, frozen specification, ISA, manifest, reference package or reference generator was changed.
