# SwapVM v1.2 executor-context implementation report

> **Historical snapshot — not the active deployment status.** This document
> records the pre-deployment v1.2 implementation phase. The current active Base
> Sepolia release is `swaputer-v1.2-rc4`; its canonical source of truth is the
> [active deployment manifest](../deployments/active/base-sepolia.json), which
> supersedes the deployment and status statements below.

Status at this snapshot: implemented locally, unaudited, not deployed.

This work starts a new experimental v1.2 line after the v1.1 Base Sepolia
zero-value deployment. It does not modify the frozen v1.1 specification, ISA or
manifest and does not change the already deployed v1.1 World.

## What changed

v1.2 adds three read-only MiniVM context opcodes:

| Opcode | Mnemonic | TinySol path | Value |
| --- | --- | --- | --- |
| `0xba` | `TXROUTER` | `tx.router` | Router address signed into the authenticated action binding. |
| `0xbb` | `TXEXECUTOR` | `tx.executor` | `authorizedExecutor` signed in the action, or zero for permissionless relay. |
| `0xbc` | `TXRECIPIENT` | `tx.recipient` | EVM recipient signed in the action. |

All three values are EVM address words: high twelve bytes zero, address in the
low 160 bits. They are inherited unchanged by nested MiniVM
`CALL`/`STATICCALL`/`CREATE`.

## Compatibility boundary

- `SwapVMKernel.VM_VERSION` is now `2`.
- `SwapVMKernel.ISA_HASH` is
  `0x5958f1a3baf744e5ed92f096a964ee14779db2e32e70a2982c53080eb3cd92c2`.
- EIP-712 domain version is now `"1.2"`.
- `VM_ACTION_TYPEHASH` and the `VMEnvelope` fields are unchanged from v1.1.
- `VMReceiptV1` and `ProgramPackageV1` encodings are unchanged.
- v1.0 and v1.1 signatures are intentionally rejected by v1.2.
- Existing v1 bytecode remains valid unless it relied on `0xba`, `0xbb` or
  `0xbc` being invalid.

## Why this exists

The immediate app-level need is escrow/vault style composition. For example, an
EVM wrapper that escrows ETH and mints an SRC20-style `sETH` inside SwapVM needs
the MiniVM program to know which EVM contract is actually executing the signed
action. With v1.2, the MiniVM program can require:

```text
require(tx.executor == trustedVault)
```

The Router still enforces that a nonzero `authorizedExecutor` equals external
`msg.sender`, and the Kernel signs the same field. The MiniVM check therefore
binds the internal mint/burn logic to a specific EVM-side entrypoint without
adding a MiniVM ETH opcode or changing receipt semantics.
